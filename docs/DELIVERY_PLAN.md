## 5. โครงฐานข้อมูล (Neon / Postgres)

วางโครงเผื่อสินค้าหลายตัวตั้งแต่ต้น แต่ตอนนี้ตาราง `product` จะมีแถวเดียว

| ตาราง | เก็บอะไร |
|---|---|
| `product` | สินค้า 1 แถวต่อ 1 เล่ม · ผูก Stripe price id → ชื่อไฟล์ใน Blob · เปิด/ปิดการประทับหน้าปก |
| `order` | 1 แถวต่อ 1 การซื้อ · Stripe session id (unique กันบันทึกซ้ำ) · อีเมล · จำนวนเล่ม · เลขออเดอร์ที่ใช้ประทับ · โควตาที่เหลือ · สถานะ (รอเงิน/จ่ายแล้ว/คืนเงินแล้ว) |
| `download_log` | 1 แถวต่อ 1 ครั้งที่กดโหลด · เวลา · เลข IP ย่อ · ใช้สืบตอนมีปัญหาและเป็นหลักฐานว่านับถูก |
| `otp` | รหัส 6 หลักที่ยังไม่หมดอายุ · เก็บเป็นค่าที่ผ่านการแฮชแล้ว ไม่เก็บตัวเลขตรง ๆ · เวลาหมดอายุ · จำนวนครั้งที่กรอกผิด |
| `rate_limit` | นับการขอรหัสต่ออีเมลต่อชั่วโมง กันคนใช้ระบบเราไปสแปมคนอื่น |

การตัดโควตาต้องทำด้วยคำสั่งเดียวแบบ atomic (`UPDATE ... SET remaining = remaining - 1
WHERE remaining > 0 RETURNING remaining`) ห้ามอ่านมาแล้วค่อยเขียนกลับ เพราะถ้ากดพร้อมกันตัวนับจะเพี้ยน

## 7. สิ่งที่เจ้าของเว็บต้องลงมือเอง (agent ทำแทนไม่ได้)

### 7.1 หลักการเรื่องลำดับ

**งานเขียนโค้ดกับงานตั้งค่าทำขนานกันได้ ไม่ต้องรอกัน** เพราะโค้ดอ้างถึงค่าเหล่านี้ผ่าน
ชื่อตัวแปรที่กำหนดไว้ล่วงหน้า ของจริงยังไม่มีก็เขียนโค้ดได้ สิ่งที่ทำไม่ได้คือ**การทดสอบ**

มีเพียงสองข้อที่มีเงื่อนไขเรื่องลำดับจริง ๆ

- **Resend + DNS ต้องเริ่มก่อนใคร** เพราะเป็นข้อเดียวที่มีเวลารอที่เราควบคุมไม่ได้
  ต้องรอ DNS กระจายและรอ Resend ยืนยันโดเมน ปกติไม่กี่นาทีแต่บางครั้งเป็นชั่วโมง
- **Stripe webhook ทำก่อน deploy ไม่ได้** เพราะ Stripe ต้องรู้ URL ปลายทางก่อนถึงจะออก
  signing secret ให้ ซึ่ง URL นั้นมีอยู่จริงก็ต่อเมื่อ deploy รอบแรกเสร็จแล้ว

ที่เหลือกดไม่กี่คลิกและไม่มีเวลารอ ทำตอนไหนก็ได้ ขอแค่เสร็จก่อนถึงรอบทดสอบ

## 12. สิ่งที่เปลี่ยนหลังใช้จริง (3 กันยายน 2569)

ทดสอบใน Stripe sandbox ครบวงจรแล้ว: จ่ายเงิน → webhook → อีเมลส่งมอบ → รหัส 6 หลัก
→ ดาวน์โหลด → watermark ตรงอีเมลตรงเลขออเดอร์ · เจ้าของเว็บลองใช้เองแล้วสั่งแก้ตามนี้

**ก. อีเมลที่ส่งไม่ออกต้องล้มดัง ๆ**
`resend.emails.send()` ไม่ throw เมื่อส่งไม่สำเร็จ แต่คืน `{ data, error }` เฉย ๆ
รอบแรกจึงเงียบสนิท ลูกค้าจ่ายเงินแล้วไม่ได้อีเมล และ webhook ตอบ 200 เหมือนไม่มีอะไรเกิดขึ้น
แก้ด้วย `sendOrThrow()` ใน `lib/delivery/mail.ts` **ห้ามถอดออก**
พร้อมกันนั้นเพิ่มคอลัมน์ `purchase.delivery_email_sent_at` แล้วเปลี่ยนตัวตัดสินใจใน webhook
จาก "เพิ่งเปลี่ยนเป็น paid ไหม" เป็น "เคยส่งอีเมลสำเร็จหรือยัง" — อีเมลล้มแล้วตอบ 500
ให้ Stripe ส่ง event ซ้ำ (ตามให้ได้ราว 3 วัน) รอบถัดไปจึงส่งใหม่ได้จริง

**ข. `RESEND_FROM` ต้องลงท้ายด้วยโดเมนที่ยืนยันไว้เท่านั้น**
ค่าที่ตั้งไว้ตอนแรกใช้ `teedba.com` แต่โดเมนที่ยืนยันกับ Resend คือ `mail.teedba.com`
Resend ตอบกลับว่า `This API key is not authorized to send emails from teedba.com`

**ค. หน้าดาวน์โหลด: หนังสือเล่มเดียวกัน = การ์ดเดียว ปุ่มเดียว**
ของเดิมแสดงหนึ่งการ์ดต่อหนึ่งออเดอร์ คนที่ซื้อเล่มเดิมสองครั้งจึงเห็นปุ่มซ้ำสองปุ่ม
และงงว่าต้องกดอันไหน ตอนนี้รวมทุกออเดอร์ของเล่มเดียวกันเข้าด้วยกัน
เหนือปุ่มบอกตรง ๆ ว่า "คุณเหลือสิทธิดาวน์โหลดได้อีก N ครั้ง" (N = ผลรวมของทุกออเดอร์)

**ง. ใบผ่าน 15 → 30 นาที และต่ออายุทุกครั้งที่โหลดสำเร็จ**
ลูกค้าเปิดหน้าค้างไว้แล้วกดโหลดทีหลัง เจอใบผ่านหมดอายุ
คนที่ยังใช้งานอยู่จึงไม่มีวันโดนเตะออกกลางคัน ส่วนคนที่ปิดหน้าไปแล้วใบผ่านหมดอายุตามเดิม
(ไม่ได้กลายเป็นการจำเครื่องถาวร ซึ่งขัดกับ decision ข้อ 3 ในตาราง §2)

**จ. ⚠️ เปลี่ยน decision เดิม — คืนโควตาอัตโนมัติเมื่อระบบเราพังเอง**
ของเดิม §10 ข้อ 3 เขียนไว้ว่าไม่คืนโควตาอัตโนมัติ เพราะกลัวมีคนหาวิธีทำให้ขั้นตอนล้มซ้ำ ๆ
แล้วโหลดได้ไม่จำกัด **เจ้าของยืนยันเปลี่ยนเมื่อ 3 ก.ย. 2569** ให้คืนสิทธิ์อัตโนมัติ
เฉพาะกรณีที่ตัดโควตาไปแล้วแต่สร้างไฟล์ล้มเพราะฝั่งเรา (ดึงจาก Blob ไม่ได้ / ประทับ watermark ล้ม)
ผ่าน `refundDownload()` — **ยังไม่คืน**เมื่อเน็ตลูกค้าหลุดกลางทาง เพราะเซิร์ฟเวอร์แยกไม่ออก
ว่าไฟล์ถึงปลายทางครบหรือยัง ถ้าคืนกรณีนั้นด้วย คนที่ตั้งใจโกงก็แค่ตัดการเชื่อมต่อทุกครั้ง

**ฉ. ยังไม่กดปุ่มดาวน์โหลด = ยังไม่เสียสิทธิ์**
โควตาถูกตัดตอนที่ route เริ่มสร้างไฟล์เท่านั้น ด่านตรวจใบผ่านอยู่ก่อนหน้านั้น
ใบผ่านหมดอายุจึงตอบ 401 โดยไม่แตะโควตา และหน้าเว็บโหลดไฟล์ผ่าน `fetch`
เพื่อดักข้อผิดพลาดเอง ลูกค้าจะไม่เจอหน้า JSON ดิบ ๆ อีก
