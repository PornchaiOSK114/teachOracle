เปิดหน้าจอมาเจอชื่อลูกค้าเป็น `???????` ทั้งตาราง — นี่คือปัญหาที่ผมเจอซ้ำแล้วซ้ำอีกตลอด 20 ปี
และเกือบทุกครั้งสาเหตุเดียวกัน: **ตั้ง character set ผิดตั้งแต่วันที่สร้างฐานข้อมูล**

ข่าวร้ายคือข้อมูลที่กลายเป็น `?` ไปแล้ว **กู้กลับไม่ได้** ข่าวดีคือตรวจสอบได้ใน 3 นาที
และถ้ารู้ทันก่อนข้อมูลเข้าเยอะ ยังแก้ได้

## ทำไมภาษาไทยถึงกลายเป็นเครื่องหมายคำถาม

Oracle เก็บตัวอักษรเป็น "รหัสตัวเลข" ตามมาตรฐานที่เรียกว่า **character set**
เมื่อไคลเอนต์ส่งข้อมูลเข้ามา Oracle จะ*แปลง*จาก character set ของไคลเอนต์ ไปเป็นของฐานข้อมูล

ถ้าฐานข้อมูลใช้ character set ที่**ไม่มีที่ว่างสำหรับอักษรไทย** เช่น `US7ASCII` (เก็บได้แค่ 128 ตัวอักษรแรกของ ASCII)
Oracle จะแทนอักษรที่เก็บไม่ได้ด้วยตัวแทนมาตรฐานคือ `?`

```text
ไคลเอนต์ส่ง:  "สวัสดี"  (UTF-8: 18 bytes)
       ↓  Oracle แปลงเป็น US7ASCII
เก็บลงจริง:   "??????"  ← อักษรไทยหายถาวร กู้ไม่ได้
```

<Callout type="danger" title="จุดที่คนพลาดบ่อยที่สุด">
การแปลงนี้เกิดขึ้น **ตอนเขียนข้อมูลลงฐานข้อมูล** ไม่ใช่ตอนแสดงผล
เมื่อข้อมูลกลายเป็น `?` แล้ว การไปแก้ `NLS_LANG` หรือเปลี่ยน character set ทีหลัง
**ไม่ช่วยให้ข้อมูลเดิมกลับมา** เพราะต้นฉบับถูกทิ้งไปตั้งแต่วินาทีที่ INSERT
</Callout>

### character set ที่เจอบ่อยในไทย

| Character Set | เก็บภาษาไทยได้ | ขนาดต่อตัวอักษรไทย | ควรใช้ไหม |
| :--- | :---: | :---: | :--- |
| `AL32UTF8` | ✅ ได้ | 3 bytes | ✅ **ใช้อันนี้** — เก็บได้ทุกภาษาในโลก |
| `TH8TISASCII` | ✅ ได้ | 1 byte | ⚠️ ได้แต่ไทย+อังกฤษ ระบบสมัยใหม่ไม่ควรใช้ |
| `WE8ISO8859P11` | ✅ ได้ | 1 byte | ⚠️ เหมือนข้างบน (มาตรฐาน ISO ของ TIS-620) |
| `WE8ISO8859P1` | ❌ ไม่ได้ | — | 🛑 ยุโรปตะวันตก — ไทยกลายเป็น `?` |
| `WE8MSWIN1252` | ❌ ไม่ได้ | — | 🛑 เหมือนข้างบน |
| `US7ASCII` | ❌ ไม่ได้ | — | 🛑 **ต้นเหตุของเคสนี้** |

> ตั้งแต่ Oracle Database 12c เป็นต้นมา Oracle แนะนำ `AL32UTF8` เป็นค่ามาตรฐาน
> และตั้งแต่ 18c เป็นต้นไป `AL32UTF8` เป็นค่าเริ่มต้นของ Database Configuration Assistant อยู่แล้ว

ภาพรวมของสิ่งที่เกิดขึ้นเป็นแบบนี้ — เส้นทางเดียวกันแต่ปลายทางต่างกันคนละโลก

สังเกตว่าฝั่งไคลเอนต์ส่งไบต์ชุดเดียวกันทั้งสองเส้นทาง สิ่งที่ต่างคือ**ปลายทางเก็บได้หรือไม่ได้**เท่านั้น

## ตรวจสอบ 3 ชั้น ใน 3 นาที

ปัญหา character set มี 3 จุดที่ต้องดู และต้องดู**ให้ครบทั้งสาม** เพราะแต่ละจุดทำให้เกิดอาการต่างกัน

![แผนภาพสามชั้นที่ต้องตรวจสอบ ได้แก่ ชั้นฐานข้อมูลดูที่ NLS_CHARACTERSET ชั้นไคลเอนต์ดูที่ตัวแปร NLS_LANG และชั้นคอลัมน์ดูที่การนับความยาวแบบไบต์หรือตัวอักษร](/images/blog/nls-three-layers.png)

ความผิดพลาดที่พบบ่อยที่สุดคือแก้แค่ชั้นเดียวแล้วคิดว่าจบ

### ชั้นที่ 1 — ฐานข้อมูล

```sql
SELECT parameter, value
  FROM nls_database_parameters
 WHERE parameter IN ('NLS_CHARACTERSET', 'NLS_NCHAR_CHARACTERSET');
```

ผลลัพธ์ที่ควรเห็น

```text
PARAMETER                 VALUE
------------------------- ------------------
NLS_CHARACTERSET          AL32UTF8
NLS_NCHAR_CHARACTERSET    AL16UTF16
```

ถ้า `NLS_CHARACTERSET` เป็น `US7ASCII` หรือ `WE8ISO8859P1` — **เจอต้นเหตุแล้ว**

### ชั้นที่ 2 — ไคลเอนต์ (ตัวแปร NLS_LANG)

ฝั่งเครื่องที่เชื่อมต่อเข้ามาต้องประกาศว่าตัวเองส่งข้อมูลมาด้วย character set อะไร

```bash
# Linux / macOS
export NLS_LANG=THAI_THAILAND.AL32UTF8
echo $NLS_LANG

# Windows (Command Prompt)
set NLS_LANG=THAI_THAILAND.AL32UTF8
```

รูปแบบคือ `ภาษา_ประเทศ.character_set` — ส่วนที่มีผลต่อการแปลงข้อมูลคือ **หลังจุด** เท่านั้น

ตรวจจากในฐานข้อมูลว่าเซสชันปัจจุบันใช้อะไรอยู่

```sql
SELECT USERENV('LANGUAGE') AS session_nls FROM dual;
```

### ชั้นที่ 3 — ดูไบต์จริงที่เก็บอยู่

นี่คือคำสั่งที่ผมใช้บ่อยที่สุดเวลาต้องพิสูจน์ว่าข้อมูลเสียไปแล้วจริงหรือไม่

```sql
SELECT customer_name,
       DUMP(customer_name, 1016) AS raw_bytes,
       LENGTH(customer_name)     AS len_chars,
       LENGTHB(customer_name)    AS len_bytes
  FROM customers
 WHERE customer_id = 1001;
```

`DUMP(..., 1016)` แสดงไบต์จริงเป็นเลขฐานสิบหกพร้อมชื่อ character set

```text
RAW_BYTES
--------------------------------------------------
Typ=1 Len=6 CharacterSet=US7ASCII: 3f,3f,3f,3f,3f,3f
```

<Callout>
`3f` คือรหัสฐานสิบหกของเครื่องหมาย `?` — เห็นแบบนี้แปลว่า**ข้อมูลต้นฉบับหายไปแล้ว**
ไม่ต้องเสียเวลาหาวิธีกู้จากในฐานข้อมูล ให้ไปหาจากไฟล์ต้นทางหรือ backup แทน
</Callout>

## กับดักที่อันตรายกว่า ??? คือ "ดูเหมือนใช้ได้"

นี่คือส่วนที่ผมอยากเน้นที่สุด เพราะเป็นสถานการณ์ที่**อันตรายกว่า** อาการ `???` มาก

ถ้าไคลเอนต์ตั้ง `NLS_LANG` เป็น character set **เดียวกัน** กับฐานข้อมูล
Oracle จะถือว่า "ไม่ต้องแปลง" แล้วส่งไบต์ผ่านไปตรง ๆ เรียกว่า **pass-through**

```text
NLS_LANG = .US7ASCII   +   DB = US7ASCII
        ↓
Oracle ไม่แปลงอะไรเลย → ไบต์ TIS-620 ของไทยถูกยัดเข้าไปดิบ ๆ
        ↓
เปิดดูจากเครื่องเดิม → เห็นภาษาไทยปกติ ✅  (แต่เป็นภาพลวงตา)
เปิดจากเครื่องอื่น / เว็บ / รายงาน → มั่วหมด ❌
```

ระบบจึงดู "ปกติดี" ไปหลายปี จนวันที่ต้องต่อ API, ทำ Data Warehouse หรือย้ายขึ้นคลาวด์
ถึงจะระเบิดพร้อมกันทั้งหมด — และตอนนั้นข้อมูลมีเป็นสิบล้านแถวแล้ว

<Callout type="warning" title="วิธีจับกับดักนี้">
ถ้า `NLS_CHARACTERSET` เป็น `US7ASCII` แต่ยัง**เห็นภาษาไทยได้ปกติ** อย่าเพิ่งดีใจ
ให้รัน `LENGTHB()` เทียบกับ `LENGTH()` ดู — ถ้าค่าเท่ากันทั้งที่เป็นภาษาไทย
แปลว่ากำลังเจอ pass-through อยู่ ไม่ใช่ระบบที่ตั้งค่าถูก
</Callout>

✏️ *[จุดนี้เหมาะจะใส่เคสจริงที่อาจารย์เคยเจอ — ระบบอะไร เจอตอนไหน เสียหายแค่ไหน]*

## VARCHAR2(10) เก็บภาษาไทยได้แค่ 3 ตัว

อีกปัญหาที่ตามมาคู่กันเสมอ แม้จะตั้ง `AL32UTF8` ถูกต้องแล้วก็ตาม

โดยค่าเริ่มต้น Oracle นับความยาวคอลัมน์เป็น **ไบต์** ไม่ใช่ตัวอักษร
และอักษรไทยใน `AL32UTF8` กินพื้นที่ **3 ไบต์ต่อตัว**

<Figure
  src="/images/blog/varchar2-byte-vs-char.png"
  alt="แผนภาพเปรียบเทียบ VARCHAR2(10) แบบนับไบต์ซึ่งเก็บอักษรไทยได้เพียง 3 ตัว กับ VARCHAR2(10 CHAR) ที่เก็บได้ครบ 10 ตัว"
  caption="ช่องสีแดงคือไบต์ที่ถูกใช้ไปแล้ว — อักษรไทย 3 ตัวกินไป 9 ไบต์ ตัวที่ 4 จึงล้น"
/>

ผลที่ตามมาคือ error ที่ดูไม่เกี่ยวกับภาษาเลย

```sql
CREATE TABLE demo (name VARCHAR2(10));           -- = 10 ไบต์

INSERT INTO demo VALUES ('สวัสดีครับ');           -- 10 ตัวอักษร = 30 ไบต์
-- ORA-12899: value too large for column "DEMO"."NAME" (actual: 30, maximum: 10)
```

วิธีแก้มี 2 ทาง

1. **ระบุที่คอลัมน์** — ชัดเจนที่สุด อ่านโค้ดแล้วเข้าใจทันที

   ```sql
   CREATE TABLE demo (name VARCHAR2(10 CHAR));   -- = 10 ตัวอักษร
   ```

2. **ตั้งค่าระดับระบบ** — สะดวกแต่ต้องระวังว่าโค้ดเก่าอาจพฤติกรรมเปลี่ยน

   ```sql
   ALTER SYSTEM SET nls_length_semantics = CHAR SCOPE = BOTH;
   ```

<Callout>
ผมแนะนำวิธีที่ 1 สำหรับระบบที่มีอยู่แล้ว เพราะเห็นชัดในตัว DDL
ส่วนวิธีที่ 2 เหมาะกับโปรเจ็คใหม่ที่ตั้งค่าตั้งแต่วันแรก
</Callout>

## ตั้งผิดไปแล้ว แก้ยังไง

คำตอบขึ้นกับว่าฐานข้อมูลอยู่ในสถานะไหน

| สถานการณ์ | ทางแก้ | ความเสี่ยง |
| :--- | :--- | ---: |
| ยังไม่ขึ้น Production | สร้างฐานข้อมูลใหม่ด้วย `AL32UTF8` แล้ว import กลับ | ต่ำ |
| ขึ้นแล้ว ข้อมูลยังไม่เสีย (pass-through) | ใช้ **DMU** ย้ายไป Unicode | ปานกลาง |
| ขึ้นแล้ว ข้อมูลเป็น `?` ไปแล้ว | กู้จาก backup / ไฟล์ต้นทาง แล้วค่อยย้าย | สูง |

![แผนภาพสรุปทางเลือกในการแก้ปัญหา แบ่งตามสถานะของฐานข้อมูล พร้อมระดับความเสี่ยงต่ำ ปานกลาง และสูง](/images/blog/charset-migration-path.png)

### เครื่องมือที่ถูกต้องคือ DMU

Oracle มีเครื่องมือชื่อ **Database Migration Assistant for Unicode (DMU)**
ซึ่งจะสแกนข้อมูลทั้งหมดก่อน แล้วรายงานว่าแถวไหนจะเสียหายถ้าแปลง — ทำให้แก้ล่วงหน้าได้

```bash
# ตัวอย่างการเรียกใช้ DMU (ติดตั้งแยกจาก Oracle Database)
cd $ORACLE_HOME/dmu
./dmu.sh
```

<Callout type="danger" title="อย่าสั่ง ALTER DATABASE CHARACTER SET เอง">
คำสั่ง `ALTER DATABASE CHARACTER SET` ใช้ได้เฉพาะกรณีที่ character set ใหม่
เป็น **strict superset** ของเดิมเท่านั้น และ Oracle ไม่แนะนำให้ใช้โดยตรงมานานแล้ว

สั่งผิดเงื่อนไข = ข้อมูลเสียหายทั้งฐานโดยไม่มีสัญญาณเตือน และมักกู้ไม่ได้
ให้ใช้ DMU เสมอ
</Callout>

## สรุป

**อาการ `???` ไม่ใช่ปัญหาการแสดงผล แต่คือข้อมูลที่หายไปแล้ว** และเกิดตั้งแต่ตอน INSERT

เช็คลิสต์สำหรับฐานข้อมูลใหม่ทุกตัว

1. สร้างด้วย `AL32UTF8` เสมอ ไม่มีข้อยกเว้น
2. ตั้ง `NLS_LANG` ที่ไคลเอนต์ทุกตัวให้ตรงกับ character set จริงที่ส่งมา
3. ประกาศคอลัมน์ข้อความเป็น `VARCHAR2(n CHAR)`
4. ทดสอบด้วยการ INSERT ภาษาไทยจริงตั้งแต่วันแรก แล้วตรวจด้วย `DUMP()`

ข้อ 4 ใช้เวลา 2 นาที แต่ประหยัดงานกู้ข้อมูลได้เป็นสัปดาห์
