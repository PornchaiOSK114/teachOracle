รายงานที่ควรมีแค่หลักสิบแถว อยู่ๆ พ่นตัวเลขออกมาเป็นหลักพัน ไม่มี error โผล่ขึ้นมาสักบรรทัด หน้าจอก็ดูเรียบร้อยดีทุกอย่าง กว่าจะรู้ตัวก็ตอนมีคนสังเกตว่ายอดรวมมันเยอะเกินจริงไปไกล

ส่วนใหญ่ที่เจอเคสแบบนี้ ต้นตอมาจากการ join ตารางหลายใบแล้วลืมใส่เงื่อนไขว่าแถวไหนของตารางหนึ่งควรจับคู่กับแถวไหนของอีกตาราง ผลลัพธ์ที่ได้เรียกว่า cartesian join หรือ cartesian product

## cartesian join เกิดขึ้นได้ยังไง

เขียน SQL สไตล์เก่าที่ใส่ชื่อตารางไว้ใน FROM คั่นด้วยจุลภาค เช่น `FROM a, b` แล้วไม่มี WHERE บอกว่าแถวไหนของ a คู่กับแถวไหนของ b เลย Oracle จะตีความว่าอยากได้ทุกคู่ที่เป็นไปได้ ไม่ใช่แค่คู่ที่สัมพันธ์กันจริง

ลองนึกภาพร้านอาหารที่มีเมนู 5 อย่างกับเครื่องดื่ม 4 อย่าง ถามว่าลูกค้าสั่งเมนูไหนคู่กับเครื่องดื่มอะไรบ้าง คำตอบที่ถูกต้องต้องมาจากบิลจริงที่ลูกค้าสั่ง แต่ cartesian join จะจับทุกเมนูคู่กับทุกเครื่องดื่มเท่าที่เป็นไปได้ทั้งหมด กลายเป็น 20 คู่ทันที ทั้งที่ไม่มีใครสั่งครบขนาดนั้นจริง

<Figure src="/images/blog/cartesian-diagram.png" alt="แผนภาพเทียบ cartesian join (จับคู่ทุกแถวกับทุกแถว 1,600 คู่) กับ inner join ที่ถูกต้อง (8 คู่ที่สัมพันธ์กันจริง)" caption="employees x departments x job_history = 1,600 คู่ที่เป็นไปได้ เทียบกับ 8 คู่จริงจาก JOIN...ON" />

```sql
-- ตัวอย่าง SQL ที่ลืมเงื่อนไข join
SELECT e.last_name, d.department_name
FROM   employees e, departments d;
-- ไม่มี WHERE เชื่อม e กับ d เลย
```

จุดที่น่ากลัวคือ query แบบนี้รันผ่านฉลุย ไม่มี error ให้เห็น ได้ผลลัพธ์กลับมาจริงด้วย แค่ผลลัพธ์นั้นไม่ตรงกับความจริงเท่านั้นเอง

## ลองดูของจริงจาก lab

ผมลองสร้างสถานการณ์นี้ขึ้นจริงด้วย schema HR ซึ่งเป็น schema ตัวอย่างที่ Oracle ใช้สอนกันมานาน มีตาราง employees 20 แถว departments 8 แถว และ job_history 10 แถว

```sql
SELECT COUNT(*)
FROM   hr.employees e, hr.departments d, hr.job_history jh;

-- CARTESIAN_ROW_COUNT
-- -------------------
--                1600
```

20 คูณ 8 คูณ 10 เท่ากับ 1,600 พอดี ครบทุกคู่ที่เป็นไปได้ระหว่างสามตาราง ไม่ใช่ความสัมพันธ์จริงสักคู่เดียว ลองดูตัวอย่างสามแถวแรกที่ได้

```text
LAST_NAME     DEPARTMENT_NAME    JH_OWNER
------------- ------------------ --------
Abel          Administration     101
Davies        Administration     101
De Haan       Administration     101
```

Abel, Davies, De Haan ไม่ได้อยู่แผนก Administration จริง Oracle แค่จับชื่อทุกคนมาแปะคู่กับทุกแผนกเท่านั้น เปิด execution plan ดูจะเห็นรายละเอียดตรงกว่านั้นอีก

```text
-----------------------------------------------------------
| Id  | Operation             | Name                     |
-----------------------------------------------------------
|   0 | SELECT STATEMENT      |                          |
|   1 |  MERGE JOIN CARTESIAN |                          |
|   2 |   MERGE JOIN CARTESIAN|                          |
|   3 |    TABLE ACCESS FULL  | DEPARTMENTS              |
-----------------------------------------------------------
```

MERGE JOIN CARTESIAN ขึ้นสองรอบ ตรงกับ join สามตารางที่ไม่มีเงื่อนไขเลยสองคู่ Oracle บอกตรงๆ แบบนี้แหละว่ากำลังจับคู่ทุกอย่างกับทุกอย่างจริง

## แก้ยังไง เขียนแบบ ANSI JOIN

วิธีกันพลาดได้ดีที่สุดคือเปลี่ยนมาเขียนด้วย JOIN...ON แทนสไตล์คอมมา เพราะลืมเงื่อนไขเมื่อไหร่ Oracle จะฟ้อง syntax error ทันที ไม่ใช่เงียบแล้วรันผ่านไปเฉยๆ

```sql
SELECT e.last_name, jh.job_id, d.department_name
FROM   hr.employees e
JOIN   hr.job_history jh ON jh.employee_id = e.employee_id
JOIN   hr.departments d  ON d.department_id = e.department_id;

-- CORRECT_ROW_COUNT
-- -----------------
--                 8
```

ได้ 8 แถว ไม่ใช่ 1,600 แปดแถวนี้แหละคือของจริง

สังเกตว่า job_history มี 10 แถว แต่ join ที่ถูกกลับได้แค่ 8 เพราะ inner join ตัดแถวที่จับคู่ไม่ได้ทิ้งไปเลย มี 2 แถวใน job_history ที่ employee_id ไม่ตรงกับใครในตาราง employees ปัจจุบันแล้ว เช่นพนักงานที่ลาออกไปแล้วแต่ประวัติงานเก่ายังถูกเก็บไว้อยู่ ถ้าอยากเห็นครบทุกแถวของ job_history ต้องเปลี่ยนไปใช้ LEFT JOIN จากฝั่ง job_history แทน

## จับให้ทันตั้งแต่ต้น

นิสัยที่ช่วยได้เยอะคือเขียน JOIN...ON ทุกครั้ง เลิกใช้สไตล์คอมมาแบบเก่าไปเลย ลืมเงื่อนไขแล้ว error ทันทีย่อมดีกว่าเงียบกริบแล้วมารู้ทีหลัง อีกอย่างคือก่อนเชื่อตัวเลขในรายงาน ลองเช็ค COUNT(*) เทียบกับของจริงดูก่อน ถ้าตารางหลักมีไม่กี่พันแถว แต่รายงานพ่นออกมาเป็นหมื่น ต้องสงสัยไว้ก่อนเสมอ แล้วถ้าผลลัพธ์ดูแปลกจนไม่แน่ใจ ลองเปิด execution plan ดูสักตั้ง เจอ MERGE JOIN CARTESIAN ทั้งที่ไม่ได้ตั้งใจเขียน CROSS JOIN นั่นคือสัญญาณเตือนตรงๆ จาก Oracle เอง

## คำถามที่มักถามต่อในห้องเรียน

**ถ้าตั้งใจอยากได้ผลแบบนี้จริงๆ ต้องเขียนยังไงไม่ให้ดูเหมือนพลาด** เขียน CROSS JOIN ให้ชัดเจนไปเลยครับ `FROM a CROSS JOIN b` คนอ่านโค้ดจะรู้ทันทีว่าตั้งใจ ไม่ใช่ลืมเงื่อนไข ต่างจากสไตล์คอมมาที่แยกไม่ออกว่าลืมหรือตั้งใจ

**ทำไม join ถูกแล้วยังหายไปสองแถว** เพราะ inner join กรองเฉพาะคู่ที่จับกันได้จริงเท่านั้น สองแถวที่หายไปคือ job_history ของพนักงานที่ไม่มีอยู่ในตาราง employees ปัจจุบันแล้ว ถ้าอยากรู้ว่าหายไปแถวไหนบ้าง ลอง LEFT JOIN จาก job_history แล้วหา employee_id ที่จับคู่กับ employees ไม่ได้ดู

## สรุป

ตัวเลขผิดปกติในรายงานมักไม่ได้มาจากข้อมูลผิด แต่มาจาก join ที่ลืมเงื่อนไข ยิ่ง join หลายตารางยิ่งเสี่ยง เพราะแถวที่บวมจะคูณกันไปเรื่อยๆ ตามจำนวนตารางที่เพิ่ม ทางแก้ไม่ยาก แค่เปลี่ยนนิสัยมาเขียน ANSI JOIN ที่ระบุ ON ชัดเจนทุกครั้ง แล้วเช็คจำนวนแถวเทียบของจริงก่อนส่งรายงานทุกครั้ง

ลองไล่ดู query ที่ join หลายตารางในงานที่ดูแลอยู่ตอนนี้เลยครับ ดูว่ามีจุดไหนยังใช้สไตล์คอมมาแบบไม่มีเงื่อนไขหลงเหลืออยู่บ้าง
