เมื่อฐานข้อมูลทำงานช้าลง สิ่งแรกที่ควรทำไม่ใช่การเดาว่า "น่าจะขาด Index"
แต่คือการอ่าน **Execution Plan** เพื่อดูว่า Optimizer เลือกเส้นทางทำงานอย่างไรจริง ๆ

## เริ่มจากดูแผนการทำงานจริง

คำสั่ง `EXPLAIN PLAN` บอกได้แค่แผนที่ Optimizer *คาดว่า* จะใช้
ถ้าอยากเห็นแผนที่ใช้จริงพร้อมตัวเลขจริง ให้ดูผ่าน `DBMS_XPLAN.DISPLAY_CURSOR` แทน

```sql
-- ต้องรัน SQL ด้วย hint /*+ GATHER_PLAN_STATISTICS */ ก่อน
-- แล้วจึงเรียกดูแผนของคำสั่งล่าสุดในเซสชันนี้
SELECT *
  FROM TABLE (
         DBMS_XPLAN.DISPLAY_CURSOR (format => 'ALLSTATS LAST')
       );
```

## เทียบค่าประมาณกับค่าจริง

ในผลลัพธ์ให้ดูสองคอลัมน์นี้เป็นหลัก

| คอลัมน์ | ความหมาย |
| :--- | :--- |
| `E-Rows` | จำนวนแถวที่ Optimizer **ประเมิน** ว่าจะได้ |
| `A-Rows` | จำนวนแถว **จริง** ที่เกิดขึ้นตอนรัน |

ถ้าสองค่านี้ต่างกันหลายเท่า แปลว่า Optimizer ตัดสินใจบนข้อมูลที่ผิด
มักมีสาเหตุจากสถิติ (statistics) ล้าสมัย ให้เก็บสถิติใหม่แล้วดูแผนอีกครั้ง

```sql
BEGIN
  DBMS_STATS.GATHER_TABLE_STATS (
    ownname => 'HR',
    tabname => 'EMPLOYEES'
  );
END;
/
```

## ระวังการใส่ Index มากเกินไป

เห็น `TABLE ACCESS FULL` แล้วอย่าเพิ่งรีบสร้าง Index ทุกคอลัมน์
เพราะทุก Index ที่เพิ่มเข้ามา ฐานข้อมูลต้องไปอัปเดตตอน `INSERT` / `UPDATE` / `DELETE` ด้วย
ให้ดูจาก Predicate ที่ใช้จริงใน `WHERE` ก่อนเสมอ

> Full Table Scan ไม่ได้แปลว่าผิดเสมอไป — ถ้าต้องอ่านข้อมูลเกือบทั้งตารางอยู่แล้ว
> การสแกนทั้งตารางอาจเร็วกว่าการไล่อ่านผ่าน Index ทีละแถวด้วยซ้ำ

## สรุป

การจูน SQL คือวงจรที่ทำซ้ำ: **วัด → วิเคราะห์ → ปรับ → วัดใหม่**
และควรปรับทีละอย่าง ไม่งั้นจะแยกไม่ออกว่าอะไรคือสิ่งที่ได้ผลจริง
