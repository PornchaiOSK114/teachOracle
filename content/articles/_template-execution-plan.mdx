เมื่อฐานข้อมูลทำงานช้าลง สิ่งแรกที่ควรทำไม่ใช่การเดาว่า "น่าจะขาด Index"
แต่คือการอ่าน **Execution Plan** เพื่อดูว่า Optimizer เลือกเส้นทางทำงานอย่างไรจริง ๆ

## เริ่มจากดูแผนการทำงานจริง

คำสั่ง `EXPLAIN PLAN` บอกได้แค่แผนที่ Optimizer *คาดว่า* จะใช้
ถ้าอยากเห็นแผนที่ใช้จริงพร้อมตัวเลขจริง ให้ดูผ่าน `DBMS_XPLAN.DISPLAY_CURSOR` แทน

```sql
-- ต้องใส่ hint GATHER_PLAN_STATISTICS ตอนรัน SQL ก่อน
SELECT /*+ GATHER_PLAN_STATISTICS */
       e.employee_id, e.last_name, d.department_name
  FROM hr.employees   e
  JOIN hr.departments d ON d.department_id = e.department_id
 WHERE e.salary > 10000;

-- แล้วจึงเรียกดูแผนของคำสั่งล่าสุดในเซสชันนี้
SELECT *
  FROM TABLE (
         DBMS_XPLAN.DISPLAY_CURSOR (format => 'ALLSTATS LAST')
       );
```

## เทียบค่าประมาณกับค่าจริง

ในผลลัพธ์ให้ดูสองคอลัมน์นี้เป็นหลัก

| คอลัมน์ | ความหมาย | ถ้าผิดปกติแปลว่า |
| :--- | :--- | :--- |
| `E-Rows` | จำนวนแถวที่ Optimizer **ประเมิน** ว่าจะได้ | — |
| `A-Rows` | จำนวนแถว **จริง** ที่เกิดขึ้นตอนรัน | ต่างจาก E-Rows หลายเท่า = สถิติล้าสมัย |
| `A-Time` | เวลาจริงที่ใช้ในแต่ละขั้น | ขั้นไหนกินเวลามากที่สุดคือจุดที่ต้องแก้ |
| `Buffers` | จำนวนบล็อกที่อ่าน | สูงผิดปกติ = อ่านข้อมูลเกินจำเป็น |

ถ้า `E-Rows` กับ `A-Rows` ต่างกันมาก แปลว่า Optimizer ตัดสินใจบนข้อมูลที่ผิด
ให้เก็บสถิติใหม่แล้วดูแผนอีกครั้ง

```sql
BEGIN
  DBMS_STATS.GATHER_TABLE_STATS (
    ownname => 'HR',
    tabname => 'EMPLOYEES',
    cascade => TRUE          -- เก็บสถิติของ Index ด้วย
  );
END;
/
```

<Callout type="warning" title="ระวังบน Production">
การเก็บสถิติใหม่ทำให้ Optimizer เปลี่ยนแผนได้ทันที ซึ่งอาจทำให้ SQL อื่นที่เคยเร็วกลับช้าลง
ควรทดสอบบนระบบ test ก่อน และเก็บแผนเดิมไว้ด้วย SQL Plan Baseline
</Callout>

## ระวังการใส่ Index มากเกินไป

เห็น `TABLE ACCESS FULL` แล้วอย่าเพิ่งรีบสร้าง Index ทุกคอลัมน์
เพราะทุก Index ที่เพิ่มเข้ามา ฐานข้อมูลต้องไปอัปเดตตอน `INSERT` / `UPDATE` / `DELETE` ด้วย

<Callout>
Full Table Scan ไม่ได้แปลว่าผิดเสมอไป — ถ้าต้องอ่านข้อมูลเกือบทั้งตารางอยู่แล้ว
การสแกนทั้งตารางมักเร็วกว่าการไล่อ่านผ่าน Index ทีละแถวด้วยซ้ำ
</Callout>

ให้ดูจาก Predicate ที่ใช้จริงใน `WHERE` ก่อนเสมอ แล้วค่อยตัดสินใจ
